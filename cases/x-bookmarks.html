01 / 系统架构

采集与处理分离，浏览器只负责"看到"。

整个系统只有采集器一个环节接触 X：它读取已登录书签页的 DOM，以 status ID 为唯一去重键，增量模式遇到已知 ID 即停止。其余一切都在本地完成——任何没有浏览器的 agent 拿到 raw JSON，都能把整条管道跑完。

A

采集器 Collector

只读已登录书签页 DOM，按 status ID 去重、增量停止；滚动步长经过实测校准，保证不漏不重。

B

处理器 Processor

本地完成清洗、三级分类、媒体下载与重试，生成 Obsidian 知识卡片与主题、作者双索引。

C

校验器 Verify

对记录数一致、ID 唯一、媒体就绪、wikilink 全部可解析做全量断言，任何一项不过即报错。

03 / 工程挑战

四个真实踩过的坑，以及各自的解法。

1虚拟化列表的覆盖陷阱

X 时间线是虚拟化列表，视口外的节点根本不进 DOM，实测渲染窗口只有 4–7 条。滚动步长 4500px 时漏采 23 条；改为 600px 步长，并用双粒度扫描互相比对验证，做到零遗漏。

2长文丢失的离线修复

时间线把长文折叠到约 5 行、引用内容串进正文、长文 Article 没有正文节点——60% 以上记录受影响。新增回源修复管道按 ID 比对补全，正文总量 +73.5%；无法调和的冲突保留双语原文，绝不覆盖。

31,048 张历史卡片的迁移

旧版生成的卡片缺少自动块标记，会被新版生成器静默冻结、永远不更新。写迁移器逐卡验证三重门禁（有标题、无人工后缀、内容可证明为机器产出）后再补插标记：1048/1048 通过，0 张人工内容被改动。

4只读边界与防"复活"

全程不读 Cookie、不做任何写操作；手工删除过的书签登记进注册表——否则每次扫描都会把它们当新书签"复活"入库。哪些记录该删，始终由人决定，系统只负责执行和留痕。
